03 · Decision

选型结论

推荐路线：开源 GitOps + 自研编排

全局薄入口（路由/审批/审计）+ 按 BU 分片的执行闭环（Argo Workflows 编排 + 分片 ArgoCD 状态收敛 + 集群内 Argo Rollouts 发布策略）+ Kafka 异步化 + 一切大对象远离 etcd

为什么开源自研

  • 万级规模有充分开源验证（ArgoCD 5 万应用 / KubeVela 50 万应用）；
  • 无厂商锁定，核心链路自主可控；
  • 与现有 CI 工具自由集成。

备选：KubeVela 选项B

  • 分片内执行层用 KubeVela，省自研抽象/渲染/多集群约 2–3 人月；
  • 代价：CUE 技术栈 + Hub→集群网络可达要求；
  • PoC 并行对比后定稿（决策可后置）。

RELEASE PLATFORM05 / 10
05 · Shard

单分片设计与组件分工

组件职责规格（2500 应用）
Argo Workflows发布编排引擎（archive-to-DB + TTL GC）0.5 核 / 1 GiB
ArgoCD（分片）状态收敛；控制器分片 + repo-server 缓存2 核 / 4 GiB
Argo Rollouts金丝雀/蓝绿 + Analysis 门禁（每业务集群）集群内
多集群接入A：Agent Pull / Karmada；B：cluster-gateway按集群数
Git 仓库组 + MySQL 分区清单 Source of Truth + 发布过程数据—

双数据源原则

Git 存期望状态（可审计回滚）；DB 存过程数据（发布单/审批/批次）。大对象（日志/diff/历史）进 ES，绝不进 etcd。

限流与隔离

单分片并发发布 ≤ 50，超出经 Kafka 排队；对账按 24h 打散（jitter）防雪崩。

07 · Scale

万级规模化保障

风险保障手段
etcd / apiserver 压力大对象（历史/日志/diff）不进 CRD，进 DB/ES；控制器分片
Git 仓库爆炸按 BU 分仓库组 + sparse-checkout + repo-server 缓存（commit SHA 为 key）

API 阻塞全异步（Kafka），API 只返回发布单 ID

08 · Roadmap

落地计划与资源

期次里程碑关键内容
一期 3–4 月端到端闭环应用模型 + 单分片单集群发布 + 审批 + 审计，替代手工 kubectl/helm
二期生产级交付多分片 + 多集群 + 金丝雀 + 监控门禁自动回滚 + 封网管控
三期平台化与度量租户化、模板市场、DORA 指标、智能发布（异常检测）

前置：PoC（2 周）

单分片 2000 应用基线，A/B 路线并行压测，量化验收（调和延迟 P99 ≤ 10s、发布并发 50/分片、控制面 ≤ 4 核/8 GiB）。产出选型终稿。

人力配置

平台工程师 ×2、后端 ×2、前端 ×1、架构师 ×1（兼）。一期聚焦执行闭环，非功能项随二期建设。

09 · Risk & Next

风险与行动项

主要风险与对策

  • CUE/技术栈成本（选项B）→ PoC 设 3 天观察期，超时扣分；
  • 网络可达（选项B gateway）→ PoC 一票否决项，不可达转 A；
  • K8s 控制面瓶颈 → 同步规划 etcd/apiserver 容量；
  • 决策拖延 → A/B 分数差 <10% 默认选 A。

评审后行动项

  • 确认集群数与 BU 划分 → 定分片数；
  • 明确现有 CI 工具 → 定集成方式；
  • 启动 2 周 PoC（环境 + A/B 双路线）；
  • 输出《PoC 压测报告》锁定路线，进入一期。
