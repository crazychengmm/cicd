## 1. 单分片部署拓扑

### 1.1 拓扑图

每个分片（对应一个 BU/产品线，约 2000–3000 应用）是一套自闭环：

```
                          ┌─────────────────────────────────────────┐
                          │              分片控制平面（管理集群）            │
                          │                                         │
   全局层 ──Kafka──▶  ┌──────────────┐      ┌──────────────────────┐│
   (topic: bu-x)      │ shard-api     │◀────▶│  shard-controller     ││
                      │ (REST/gRPC)   │      │  (发布编排, leader)     ││
                      │ ×3 无状态      │      │  ×2 + leader-election ││
                      └──────┬───────┘      └──────┬───────────────┘│
                             │                     │ 创建 Workflow    │
                             │              ┌──────▼───────────────┐ │
                             │              │ Argo Workflows 实例    │ │
                             │              │ (命名空间隔离)          │ │
                             │              └──────┬───────────────┘ │
                             │                     │ 写 Git / 驱动 Rollouts
                             │              ┌──────▼───────────────┐ │
                             │              │ ArgoCD 实例（分片）     │ │
                             │              │  app-controller ×2    │ │
                             │              │  repo-server ×3       │ │
                             │              │  applicationset ×1    │ │
                             │              └──────┬───────────────┘ │
                             │                     │                  │
                      ┌──────▼───────┐      ┌──────▼───────────────┐ │
                      │ MySQL 分区     │      │ Git 仓库组             │ │
                      │ schema: bu_x  │      │ git.xxx.com/bu-x/*    │ │
                      └──────────────┘      └──────────────────────┘ │
                          └──────────────────────┬──────────────────┘
                                                 │ Pull 模式（Agent）
                    ┌────────────────────────────┼────────────────────────┐
                    ▼                            ▼                        ▼
             ┌─────────────┐            ┌─────────────┐          ┌─────────────┐
             │ 业务集群 A    │            │ 业务集群 B    │          │ 业务集群 C    │
             │ shard-agent │            │ shard-agent │          │ shard-agent │
             │ argo-rollouts│            │ argo-rollouts│         │ argo-rollouts│
             │ karmada-agent│            │ karmada-agent│         │ karmada-agent│
             └─────────────┘            └─────────────┘          └─────────────┘
```

### 1.2 组件清单与规格

| 组件 | 职责 | 副本数 | 部署位置 | 关键配置 |
|------|------|--------|----------|----------|
| **shard-api-server** | 分片对外 API（发布单 CRUD、查询、回调） | 3 | 管理集群 | 无状态，HPA |
| **shard-controller** | 发布编排核心，消费 Kafka、驱动 Workflow | 2 | 管理集群 | leader-election，单活 |
| **Argo Workflows** | 工作流执行引擎 | 1 controller | 管理集群（独立 namespace） | archive-to-DB + TTL GC |
| **ArgoCD app-controller** | 状态收敛、同步 | 2（分片） | 管理集群 | `ARGOCD_CONTROLLER_REPLICAS=2` |
| **ArgoCD repo-server** | 清单渲染 | 2–3 | 管理集群 | 开缓存，commit SHA 为 key |
| **ArgoCD applicationset-controller** | 批量生成 Application | 1 | 管理集群 | 拆多个 ApplicationSet |
| **shard-agent** | 集群内执行代理，拉任务、执行、上报 | 2（DaemonSet/Deployment） | 每个业务集群 | Pull 模式，不暴露端口给控制面 |
| **argo-rollouts** | 金丝雀/蓝绿 + Analysis | 1 controller | 每个业务集群 | 集群内自治 |
| **Kafka 分区** | 分片任务总线 | 复用全局 Kafka | — | 每分片独立 topic |
| **MySQL 分区** | 分片业务数据 | 1 主 2 从 | — | schema 按 BU 隔离 |
| **Git 仓库组** | 声明式清单 Source of Truth | — | — | 每 BU 独立仓库组，sparse-checkout |

### 1.3 分片内数据流

```
CI 构建完成
  → 调用 shard-api 创建发布单
  → shard-controller 写 MySQL + 发 Kafka 事件
  → Argo Workflows 拉起发布工作流
  → 工作流步骤：
      ① 更新 Git 仓库（新镜像 tag）
      ② 触发/等待 ArgoCD 同步
      ③ 驱动 Rollouts 分批（暂停→Analysis→晋升）
      ④ 审批节点（suspend）
  → shard-agent 上报集群执行结果
  → 工作流完成，状态回写 MySQL + 审计
```

### 1.4 容量与隔离设计要点

1. **故障隔离**：分片间完全独立，BU-X 的 ArgoCD/controller 故障不影响 BU-Y；
2. **限流**：单分片并发发布上限（建议 ≤50），超出在 Kafka 排队；
3. **etcd 保护**：Workflow 完成后立即 archive 出 etcd；发布历史、日志、diff 全部进 DB/ES，不进 CRD status；
4. **对账削峰**：漂移检测对账按 24h 均匀打散（jitter），避免万级应用同时触发 reconcile。

## 2. 核心 CRD 设计

> 设计原则：**状态收敛交给 ArgoCD，发布策略交给 Argo Rollouts**，自研 CRD 只承载发布系统自身需要编排的"发布单"语义，保持轻量。

### 2.1 ReleaseOrder（发布单）

发布系统在目标集群中创建的执行单元，一个发布单对应一次"应用在某集群的一次发布"。

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: releaseorders.release.example.com
spec:
  group: release.example.com
  scope: Namespaced
  names:
    kind: ReleaseOrder
    plural: releaseorders
    shortNames: [ro]
  versions:
    - name: v1alpha1
      served: true
      storage: true
      subresources:
        status: {}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                application:        # 应用名（平台元数据）
                  type: string
                targetVersion:      # 目标版本/镜像 tag
                  type: string
                environment:        # dev/test/staging/prod
                  type: string
                strategy:           # Rolling / Canary / BlueGreen
                  type: string
                  enum: [Rolling, Canary, BlueGreen]
                rolloutRef:         # 关联的 Argo Rollouts Rollout 名
                  type: object
                  properties:
                    name: { type: string }
                    namespace: { type: string }
                batches:            # 分批计划（Canary 用）
                  type: array
                  items:
                    type: object
                    properties:
                      weight: { type: integer }     # 流量/副本权重 %
                      pause: { type: boolean }      # 是否需人工确认
                      analysis: { type: string }    # 关联 AnalysisTemplate 名
                approvalRequired:   # 是否需审批
                  type: boolean
                changeWindowRef:    # 关联变更窗口
                  type: string
            status:
              type: object
              properties:
                phase:              # Pending/Running/Paused/Succeeded/Failed/RolledBack
                  type: string
                currentBatch: { type: integer }
                observedVersion: { type: string }
                conditions:
                  type: array
                  items:
                    type: object
                    properties:
                      type: { type: string }
                      status: { type: string }
                      reason: { type: string }
                      lastTransitionTime: { type: string, format: date-time }
```

**控制器行为**（shard-agent 内的 ReleaseOrder controller）：
- 监听 ReleaseOrder，按 `batches` 驱动关联 Rollout 的晋升/暂停；
- 每批次完成触发对应 `analysis`，失败则自动回滚并置 `phase=Failed`；
- 审批节点时置 `phase=Paused`，等待全局层审批回调后继续。

> **注意**：status 中只放轻量字段，禁止写入发布日志、diff 明细等大对象（etcd 保护）。

### 2.2 与开源 CRD 的关系

| 自研 CRD | 复用的开源 CRD | 分工 |
|----------|----------------|------|
| `ReleaseOrder` | `argoproj.io/Rollout` | ReleaseOrder 管"发布流程/批次/审批"，Rollout 管"实际流量切分与副本滚动" |
| — | `argoproj.io/AnalysisTemplate` | 批次门禁（错误率/P99）由 AnalysisTemplate 定义，ReleaseOrder 引用 |
| — | `argoproj.io/Application`（ArgoCD） | Git→集群的状态收敛，ReleaseOrder 不感知 |

### 2.3 Application（平台元数据，可选 CRD）

应用元数据**主存储在全局 DB**；如需在集群内声明式注册，可用轻量 CRD 或直接用 label 约定，二选一。多数场景建议只存 DB，避免万级 CR 进 etcd。

## 3. 发布工作流模板

### 3.1 设计说明

工作流由 Argo Workflows 执行，核心是"**GitOps 做状态收敛 + Rollouts 做策略 + suspend 做审批/分批暂停**"的联动：

1. 工作流更新 Git 仓库镜像 tag → ArgoCD 自动同步到 Rollout；
2. Rollout 的 canary steps 定义分批 + 每批 analysis 门禁；
3. 工作流在每批后 `suspend`，等待 Analysis 通过 +（可选）人工审批，然后 `promote` 晋升下一批。

### 3.2 关联的 Rollout 清单（含分批与门禁）

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: shop-service
spec:
  replicas: 20
  selector:
    matchLabels: { app: shop-service }
  template:
    metadata:
      labels: { app: shop-service }
    spec:
      containers:
        - name: app
          image: registry.example.com/shop-service:{{IMAGE_TAG}}
  strategy:
    canary:
      steps:
        - setWeight: 10
        - analysis:                    # 批次1 门禁
            templates: [{ templateName: error-rate-gate }]
        - pause: { duration: 5m }      # 观察窗（也可不设时长，纯人工）
        - setWeight: 50
        - analysis:
            templates: [{ templateName: error-rate-gate }]
        - pause: {}                    # 无限暂停，等工作流 promote
        - setWeight: 100
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: error-rate-gate
spec:
  metrics:
    - name: error-rate
      interval: 60s
      successCondition: result[0] < 0.01     # 错误率 < 1%
      failureLimit: 3
      provider:
        prometheus:
          address: http://prometheus.monitoring:9090
          query: |
            sum(rate(http_errors_total{app="shop-service"}[2m]))
            / sum(rate(http_requests_total{app="shop-service"}[2m]))
```

### 3.3 Argo WorkflowTemplate（发布编排）

```yaml
apiVersion: argoproj.io/v1alpha1
kind: WorkflowTemplate
metadata:
  name: canary-release
spec:
  entrypoint: release
  serviceAccountName: release-workflow
  arguments:
    parameters:
      - { name: app }           # 应用名
      - { name: image-tag }     # 目标镜像 tag
      - { name: cluster }       # 目标集群
      - { name: rollout }       # Rollout 名
      - { name: namespace }     # Rollout 命名空间
  templates:

    # ===== 主流程 =====
    - name: release
      steps:
        - - name: pre-check                 # 变更窗口/配额检查
            template: pre-check
        - - name: approval-gate             # 生产环境人工审批
            template: approval
            when: "{{workflow.parameters.env}} == prod"
        - - name: update-git                # 写 Git，触发 ArgoCD
            template: git-update
        - - name: wait-sync                 # 等 ArgoCD 同步完成
            template: argocd-sync
        - - name: batch-1                   # 批次1（10%）
            template: promote-batch
            arguments: { parameters: [{ name: step, value: "1" }] }
        - - name: batch-2                   # 批次2（50%）
            template: promote-batch
            arguments: { parameters: [{ name: step, value: "2" }] }
        - - name: finalize                  # 完成，回写发布单
            template: finalize

    # ===== 前置检查 =====
    - name: pre-check
      container:
        image: release-tools:latest
        command: [release-cli, precheck]
        args:
          - --app={{workflow.parameters.app}}
          - --cluster={{workflow.parameters.cluster}}

    # ===== 人工审批（suspend，可挂起数天）=====
    - name: approval
      suspend: {}
      # 全局层审批通过后调用 argo resume / 或 controller 更新 status 继续

    # ===== 更新 Git 镜像 tag =====
    - name: git-update
      container:
        image: release-tools:latest
        command: [release-cli, git-set-image]
        args:
          - --repo=git@example.com:bu-x/{{workflow.parameters.app}}.git
          - --image-tag={{workflow.parameters.image-tag}}
        env:
          - name: GIT_TOKEN
            valueFrom: { secretKeyRef: { name: git-secret, key: token } }

    # ===== 等待 ArgoCD 同步 =====
    - name: argocd-sync
      container:
        image: argoproj/argocd:latest
        command: [argocd, app, wait]
        args:
          - {{workflow.parameters.app}}
          - --sync-status=Synced
          - --health
          - --timeout=600
          - --server=argocd.bu-x.svc:8080

    # ===== 分批晋升（每批后暂停等门禁 + 可选审批）=====
    - name: promote-batch
      inputs:
        parameters: [{ name: step }]
      steps:
        - - name: promote
            template: do-promote
        - - name: wait-analysis              # 等 Rollout Analysis 通过
            template: wait-healthy
        - - name: batch-pause                # 批次间人工确认（可选）
            suspend: {}

    - name: do-promote
      container:
        image: release-tools:latest
        command: [kubectl, argo, rollouts, promote]
        args: ["{{workflow.parameters.rollout}}",
               "-n", "{{workflow.parameters.namespace}}"]

    - name: wait-healthy
      container:
        image: release-tools:latest
        command: [kubectl, argo, rollouts, status, --watch]
        args: ["{{workflow.parameters.rollout}}",
               "-n", "{{workflow.parameters.namespace}}"]

    # ===== 完成回写 =====
    - name: finalize
      container:
        image: release-tools:latest
        command: [release-cli, finalize]
        args:
          - --order={{workflow.name}}
          - --result=Succeeded

  # 失败/超时自动回滚钩子
  onExit: rollback-on-failure
  templates-ignore: []
---
    - name: rollback-on-failure
      container:
        image: release-tools:latest
        command: [release-cli, rollback]
        args:
          - --rollout={{workflow.parameters.rollout}}
          - --namespace={{workflow.parameters.namespace}}
          - --order={{workflow.name}}
```

> 说明：
> - `suspend` 节点实现"可暂停、可审批"，由全局审批系统驱动恢复；
> - `onExit` 钩子保证任何失败/超时都触发 Rollout 回滚；
> - `release-cli` 为自研薄封装工具（git 操作、precheck、finalize），是少数需要自研的部分。

## 4. 分片 DB 表结构设计

### 4.1 分库策略

| 数据 | 归属 | 分片键 | 说明 |
|------|------|--------|------|
| 应用元数据、环境、分片路由 | **全局库** | — | 全局唯一入口读写 |
| 发布单、批次、审批、审计 | **分片库**（每 BU 一个 schema） | `app_id` | 片内闭环，跨片不 join |
| 发布历史、日志、diff | **ES / 对象存储** | — | 不进 MySQL，更不进 etcd |

### 4.2 全局库表

```sql
-- 应用元数据
CREATE TABLE application (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  app_name      VARCHAR(128) NOT NULL UNIQUE,
  app_type      VARCHAR(32)  NOT NULL,          -- service/job/middleware
  owner_team    VARCHAR(64)  NOT NULL,
  risk_level    TINYINT      NOT NULL DEFAULT 1, -- 1低 2中 3高
  repo_url      VARCHAR(256),
  status        TINYINT      NOT NULL DEFAULT 1,
  created_at    DATETIME     NOT NULL,
  updated_at    DATETIME     NOT NULL,
  KEY idx_owner (owner_team)
);

-- 应用 -> 分片路由
CREATE TABLE shard_route (
  app_id    BIGINT NOT NULL,
  shard_id  INT    NOT NULL,                    -- 所属分片
  cluster   VARCHAR(64),
  PRIMARY KEY (app_id),
  KEY idx_shard (shard_id)
);

-- 环境定义
CREATE TABLE environment (
  id        INT PRIMARY KEY AUTO_INCREMENT,
  env_name  VARCHAR(32) NOT NULL UNIQUE,         -- dev/test/staging/prod
  risk      TINYINT NOT NULL,
  approval_required TINYINT NOT NULL DEFAULT 0
);

-- 变更窗口/封网
CREATE TABLE change_window (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  env_name   VARCHAR(32) NOT NULL,
  start_time DATETIME NOT NULL,
  end_time   DATETIME NOT NULL,
  type       VARCHAR(16) NOT NULL,               -- ALLOW / FREEZE
  reason     VARCHAR(256),
  KEY idx_env_time (env_name, start_time)
);
```

### 4.3 分片库表（每个 BU schema 内）

```sql
-- 发布单
CREATE TABLE release_order (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_no       VARCHAR(64) NOT NULL UNIQUE,    -- 全局唯一单号
  app_id         BIGINT NOT NULL,                -- 分片键
  app_name       VARCHAR(128) NOT NULL,
  env_name       VARCHAR(32) NOT NULL,
  cluster        VARCHAR(64) NOT NULL,
  target_version VARCHAR(128) NOT NULL,          -- 镜像 tag
  strategy       VARCHAR(16) NOT NULL,           -- Rolling/Canary/BlueGreen
  phase          VARCHAR(16) NOT NULL,           -- 状态机
  workflow_name  VARCHAR(64),                    -- 关联 Argo Workflow
  approval_required TINYINT NOT NULL DEFAULT 0,
  created_by     VARCHAR(64) NOT NULL,
  created_at     DATETIME NOT NULL,
  updated_at     DATETIME NOT NULL,
  finished_at    DATETIME,
  KEY idx_app_time (app_id, created_at),
  KEY idx_phase (phase)
);

-- 发布批次
CREATE TABLE release_batch (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_id     BIGINT NOT NULL,                  -- 分片键=发布单
  batch_no     INT NOT NULL,
  weight       INT NOT NULL,                     -- %
  phase        VARCHAR(16) NOT NULL,             -- Pending/Running/Done/Failed
  analysis_result VARCHAR(16),                   -- Pass/Fail
  started_at   DATETIME,
  finished_at  DATETIME,
  KEY idx_order (order_id)
);

-- 审批记录
CREATE TABLE approval_record (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_id    BIGINT NOT NULL,
  approver    VARCHAR(64) NOT NULL,
  action      VARCHAR(16) NOT NULL,              -- APPROVE/REJECT
  comment     VARCHAR(512),
  acted_at    DATETIME NOT NULL,
  KEY idx_order (order_id)
);

-- 审计日志（操作留痕，明细可下沉 ES）
CREATE TABLE audit_log (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  app_id      BIGINT NOT NULL,                   -- 分片键
  order_id    BIGINT,
  actor       VARCHAR(64) NOT NULL,
  action      VARCHAR(64) NOT NULL,
  detail_ref  VARCHAR(256),                      -- 指向 ES 明细
  created_at  DATETIME NOT NULL,
  KEY idx_app_time (app_id, created_at)
);
```

### 4.4 发布单状态机

```
Pending ──▶ AwaitingApproval ──▶ Running ──▶ Succeeded
   │              │                  │
   │              └──▶ Rejected      ├──▶ Paused ──▶ Running
   │                                 │
   └──▶ Failed ◀────────────────────┴──▶ RolledBack
```

## 5. 评审 PPT 大纲

> 目标听众：技术评审委员会 / 架构组。建议 10 页，20 分钟。

| # | 页标题 | 核心内容 | 关键信息 |
|---|--------|----------|----------|
| 1 | 封面 | 企业级发布系统设计评审 | 目标：万级应用、开源自研 |
| 2 | 背景与目标 | 现状痛点、业务规模、建设目标 | 1万+应用、多集群、合规要求 |
| 3 | 方案调研总览 | OAM / 非OAM开源 / 商业 / 信创 四条路线 | 一页对比表 |
| 4 | 选型结论 | 为什么选"开源 GitOps + 自研编排" | 无锁定、万级验证、可控 |
| 5 | 总体架构 | 全局薄层 + 分片执行 全景图 | 分片是万级的关键 |
| 6 | 单分片设计 | 分片内组件拓扑 + 数据流 | Argo Workflows/ArgoCD/Rollouts 分工 |
| 7 | 发布流程 | 一次发布的完整时序 + 分批/审批/回滚 | 工作流图 |
| 8 | 规模化保障 | etcd 保护、对账削峰、限流、隔离 | 万级防坑清单 |
| 9 | 落地计划 | 一/二/三期里程碑 + 资源估算 | 一期 3~4 个月 |
